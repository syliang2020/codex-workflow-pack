# Superpowers 兼容约定

本文件处理 Superpowers 7.x 与 router 的交接边界，不复制上游计划模板或脚本实现。阶段顺序仍以 `workflows/*.md` 为准；用户当前指令和适用 `AGENTS.md` 始终优先。升级时更新本地 router，不修改 Superpowers 上游源码。

## 执行方式与授权

在 `writing-plans` 交接时连同计划确认执行方式。用户已明确选择时沿用，不重复提问。

| 执行方式 | 使用的技能 | 实现职责 | 审查 |
| --- | --- | --- | --- |
| `inline` | `superpowers:executing-plans` | 主 agent 实现各任务，不派发实现型子代理 | 在 router 编码后审查阶段安排一次最终通用审查 |
| `subagent-driven` | `superpowers:subagent-driven-development` | 已授权的专业子代理分任务实现 | 保留执行器的逐任务审查，router 统筹最终通用审查 |

- 工具存在、角色已安装、计划已确认均不等于子代理已获授权。每次派发都检查用户指令、适用 `AGENTS.md`、当前模式及任务边界。
- 只有适用规则明确允许时，已确认的 direct-flow 才能作为授权依据；项目规则要求明确请求子代理时，不得用全局例外绕过。
- `prompt-preview` 当前不启动任何子代理；`review-only`、session diagnosis、builder check 和 inline 的最终审查均不自带派发授权。
- `subagent-driven` 未获授权或不可用时，不启动它；提出 `inline` 替代并随计划确认，不能静默更换执行方式。已有“不要子代理”指令时直接遵守。
- `inline` 中需要后端、前端、API、SQL 或 UI 专业职责时，由主 agent 执行这些职责；不得声称已启动同名角色，也不能把主动选择 inline 描述为工具不可用。
- 修复、回归失败和联调修正返回已确认的执行阶段，不在两种执行器间来回切换，不为同一计划重建另一份进度台账。

## 设计与文档

- feature 的 brainstorming 用于需求和设计，先复用已有资料，只追问会改变交付结果的问题。它结束后先回到 workflow 的协同设计和设计门禁，再进入计划阶段；不直接跳过这些阶段。
- 后端设计门禁命中时，按 `AGENTS.md` 展示审查结论并等待确认。需要与计划合并确认时，必须展示两份具体产物并明确确认范围，不能把认可需求自动当成设计或计划批准。
- 合并确认前的设计与计划均标注待确认，不把待确认输入写成已确认事实；在确认到来前仅准备草案，不修改业务代码。后续专业设计改变已确认内容时，更新同一设计来源并针对变化确认，保持计划的设计引用有效。
- 协作文档包按 `AGENTS.md` 和 `feature-doc-pack` 先判断、先询问；用户拒绝后不生成，不因 Superpowers 自动流程而新增另一套协作文档。
- Superpowers 的设计输入、实现计划、运行台账与团队协作文档各有用途，优先引用已有等价资料，避免重复。文件范围有歧义时先澄清一次，不通过换文件名规避用户的文档选择。
- 用户明确拒绝任何文档落盘时，不偷偷创建计划。先在对话中给出可审查的设计或计划，并说明文件驱动执行器需要的最小输入；获准落盘前不启动依赖计划文件的脚本。
- 文档正文默认中文、UTF-8；计划保留上游脚本需要的 `Task N`、`Spec`、`Global Constraints`、`Interfaces`、`Review Focus` 等结构标识，具体格式以实际加载的新版技能为准。

## 执行器与 router 的阶段交接

调用执行器时明确传递：计划与设计来源、`execution_mode`、子代理授权依据、可修改范围、设计确认状态、测试约束，以及“最终审查和 Finish 由 router 托管”。这组限制同样传给实现和审查子代理。

1. **实现阶段**：运行所选执行器的准备、任务循环、TDD、逐任务检查和进度记录。此时不执行其最终 workspace 删除或 `finishing-a-development-branch`。不得把整个技能不分阶段跑完后再回到 router 补门禁。
2. **编码后审查阶段**：将后端分层、UI、接口契约等专业检查并入审查输入，在本阶段执行所选执行器的最终通用审查。已获得等价且覆盖当前 diff 的审查结果时直接复用，不再额外启动一轮同范围通用审查。
3. **联调和最终验证阶段**：按 workflow 完成项目测试和必要浏览器验证。后续发生代码变更时，修复后补审变更范围并重新验证受影响路径，保证验收针对最终版本。
4. **验收阶段**：核对专业门禁、最终版本审查与验证结果，汇总真实未完成项和用户需要知道的执行裁决；验收资料齐备后才进入分支收尾。合并、推送、发布等操作遵守用户授权，不因进入 Finish 而自动获准。

`inline` 不在任务之间反复询问“是否继续”。需要确认的设计、计划、范围变化、权限或破坏性操作仍必须停下；具体实现细节在授权范围内按上游方式记录裁决并继续。

## 审查执行者与质量门禁

- 编码后审查先检查授权。已获授权且工具可用时，代码审查派给只读 `reviewer`；领域 skill 补充相应检查，不把代码审查派给实现角色。
- 没有授权、当前模式禁止或工具不可用时，由主 agent 单独进行自查，准确注明原因和执行者；不得称为独立审查或假装代理已执行。项目规则要求独立审查且无法满足时，如实标为待满足的门禁，不宣布验收通过。
- 按实际影响和来源分类：历史问题、本次新增问题、本次扩大的历史问题。**本次新增或扩大的真实缺陷必须修复，包含被上游标为 Minor 的缺陷。** 纯风格偏好、需求外增强与历史问题单独报告，不借修复之名扩大范围。
- 上游的修复轮次上限用于防止无效循环，不能豁免本次缺陷。达到上限后保留证据、定位根因；无法闭环时列为未完成，不把未通过门禁的代码报告为可交付。
- 执行器已完成的测试证据可以复用。最终验证按项目约定运行测试套件；只通过目标文件的测试不能称整个套件通过。失败项逐项说明来源和影响，未运行的检查如实标记 `not-run`。

## 临时产物和清理

- 运行文件由所选执行器按实际版本管理，router 记录当前计划的 workspace 和台账路径，不硬编码另一个工作区命名规则。
- 清理前将执行裁决、未解决问题和验证结果纳入交付输出。台账是执行记录，不能用“已提交代码”替代尚未导出的证据。
- 删除 workspace、台账、临时文件、分支或 worktree 都服从适用的删除确认规则。说明具体路径、理由和影响；已有明确授权只覆盖其范围，不重复询问同一删除动作。
- 未获授权时保留并报告路径，不执行上游自动清理，也不把待清理状态误报为业务实现失败。不得清理其他计划目录或修改用户的未提交文件。
- Windows 下只在核对绝对路径及所属范围后使用原生文件操作；不拼接跨 shell 的递归删除或移动命令。

## Codex 工具适配

- 实际工具定义、允许的角色与模型优先于上游平台参考。调用前核对当前 schema；不把示例参数当作本机必然支持的能力。
- 按任务选择角色，模型与 reasoning effort 仅在当前工具和角色允许时设置；不覆盖固定角色配置，不照抄旧会话中的模型名。
- 需要覆盖模型而完整历史 fork 不允许覆盖时，使用工具支持的隔离上下文，并在任务交接中提供最小必要输入。不为满足上游样例而提交不支持的参数组合。
- 等待、恢复子代理和生命周期管理按实际工具执行；主 agent 有其他独立工作时先推进工作，不用短轮询制造重复调用。
- 本 skill 不自动修改 `config.toml`、默认模型、Node 环境或上游源码。必须调整环境时先说明必要性，并按用户既有授权处理。
