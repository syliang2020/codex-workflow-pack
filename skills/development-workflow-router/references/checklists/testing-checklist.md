# Testing Checklist

适用于开发、修复、联调和验收阶段。

测试策划和执行读取 [system-testing](../../../system-testing/SKILL.md)。明确范围、环境、版本、数据权限与参照组件；只测试时不自动修复业务代码。

## 功能、视觉与过程

- 功能正确性、静态视觉、交互过程分别报告适用性、状态和证据，不以功能通过代替页面验收。
- 页面覆盖受影响的正常、空数据、长文本、校验错误、加载与失败状态，以及实际支持的窗口尺寸；记录未覆盖项，不机械穷举。
- 静态视觉检查重叠、遮挡、溢出、裁切、对齐和间距，依据项目现有组件与同类页面；正常浮层、内部滚动和明确的省略行为不盲目报错。
- 交互过程通过真实操作检查加载、弹窗、展开、滚动与窗口变化；必要时保留视频、连续截图或位置时序，最终截图不能代替过程证据。
- UI 规范与体验判断使用 `ui-ux-pro-max`，服从项目已确认标准；没有依据的审美意见列为建议或待确认。
- 按风险使用只读 `qa-expert` 策划覆盖；需要自动化脚本时，在授权范围内使用 `test-automator`，或由主 agent 实现，不擅自安装测试框架。
- 任一适用维度 `failed`，整体未通过；无失败但有适用项 `not-run`，整体未完成验证。不适用项说明理由，不记录虚假通过。

## 测试类型

根据任务选择：

1. 编译检查。
2. 单元测试。
3. 接口测试。
4. 前端构建测试。
5. 类型检查。
6. Lint 检查。
7. 前后端联调。
8. Playwright 或浏览器真实测试。
9. 回归测试。

复用已完成且仍覆盖当前版本的验证证据，不因进入另一阶段重复跑同一轮。最终按项目约定运行测试套件，只有目标测试通过时不得声称整体套件通过；用户指定测试例外时如实记录验证范围。

## 测试结果状态

每个测试必须标记为：

- `passed`：测试通过。
- `failed`：测试失败。
- `not-run`：未运行。

## failed 处理

如果测试失败：

1. 不得直接进入验收。
2. 必须定位失败原因。
3. 如果是本次改动导致，必须修复并重跑。
4. 如果是历史遗留问题，必须说明证据和影响。
5. 验收报告必须记录失败项和处理结论。

## not-run 处理

如果测试未运行：

1. 必须说明未运行原因。
2. 必须说明风险。
3. 必须给出用户可执行的验证命令。
4. 不得把 `not-run` 描述成 `passed`。
