# Backend Bugfix Workflow

后端 bugfix 用于问题边界主要在服务端、接口、权限、数据查询、事务、保存编辑逻辑或后端测试失败的场景。只要问题需要页面复现或前端改动，必须考虑 `fullstack-bugfix`。

## 阶段

### 1. Bug 复现与系统化调试

- 使用：
  - `superpowers:systematic-debugging`
  - `debugger`
- 输入：
  - 报错信息
  - 失败测试
  - 用户描述
  - 相关日志或请求参数
- 输出：
  - 可复现步骤
  - 实际现象
  - 期望现象
  - 影响范围
  - 初步根因假设
- 是否允许改代码：否。
- 是否需要用户确认：复现信息不足或影响范围不清时需要确认。
- 执行要求：
  - 不得跳过 bug-reproduce。
  - `debugger` 不可用时，主 agent 必须按同等职责定位并说明原因。

---

### 2. 根因定位

- 使用：
  - `superpowers:systematic-debugging`
  - `debugger`
- 输入：
  - 复现结果
  - 相关后端代码
  - 测试和日志
- 输出：
  - 已验证根因
  - 受影响调用链
  - 数据来源和权限影响
  - 回归风险
- 是否允许改代码：否。
- 是否需要用户确认：根因不唯一或修复会改变业务行为时需要确认。
- 执行要求：
  - 修复会新增功能或改变业务行为时，必须补充 `superpowers:brainstorming` 再进入修复设计。

---

### 3. 修复方案设计

- 使用：
  - `api-designer`
  - `sql-pro`
  - `backend-feature-design-review`
- 输入：
  - 已验证根因
  - 受影响接口、Service、Mapper/DAO/Repository、SQL
  - 历史数据和兼容性约束
- 输出：
  - 修复方案
  - 回归测试点
  - API 兼容性结论
  - 数据库或 SQL 风险
  - 后端设计门禁结论
- 是否允许改代码：否。
- 是否需要用户确认：修复影响接口、数据库、权限、历史数据或行为语义时需要确认。
- 执行要求：
  - 涉及接口契约时使用 `api-designer`。
  - 涉及 SQL、索引或数据口径时使用 `sql-pro`。
  - 涉及复杂后端结构时使用 `backend-feature-design-review`。

---

### 4. `superpowers:writing-plans`

- 使用：
  - `superpowers:writing-plans`
- 输入：
  - 根因定位结果
  - 修复方案
  - 回归测试点
  - 项目测试约束
- 输出：
  - 文件级修复计划
  - 回归测试计划
  - 风险和回滚方案
  - 子代理分工计划
- 是否允许改代码：否。
- 是否需要用户确认：是，计划未确认前不得实现。
- 执行要求：
  - 计划必须体现 `superpowers:executing-plans with TDD`。
  - 必须说明如何证明根因被修复。

---

### 5. 用户确认

- 使用：
  - 主 agent
- 输入：
  - 修复计划
  - 风险和回归测试点
- 输出：
  - 用户确认结果
  - 需要调整的计划
- 是否允许改代码：否。
- 是否需要用户确认：是。
- 执行要求：
  - 用户未确认前不得修改代码或启动实现型 subagent。

---

### 6. `superpowers:executing-plans` with TDD

- 使用：
  - `superpowers:executing-plans`
  - `spring-boot-engineer`
- 输入：
  - 已确认的修复计划
  - 回归测试计划
  - 可修改范围
- 输出：
  - 后端修复
  - 回归测试
  - 实际修改文件
  - 偏离计划的说明
- 是否允许改代码：是，仅限用户确认后的计划范围。
- 是否需要用户确认：进入本阶段前需要确认；偏离计划时需要再次确认。
- 执行要求：
  - 优先补能复现 bug 的失败测试，再修复。
  - 后端修复优先交给 `spring-boot-engineer`；不可用时主 agent 替代并说明。

---

### 7. 子代理交接与回收

- 使用：
  - 主 agent
  - 已启动的 subagents
  - `references/review-and-handoff.md`
- 输入：
  - subagent 交付结果
  - 修复 diff
  - 回归测试输出
- 输出：
  - 子代理交接摘要
  - 根因修复核对
  - 主 agent 回收结论
- 是否允许改代码：必要时允许，但只能处理集成缺口和冲突。
- 是否需要用户确认：交接结果改变计划或风险升高时需要确认。
- 执行要求：
  - 未启动的计划内 subagent 必须说明原因并给出主 agent 替代产出。

---

### 8. 代码审查

- 使用：
  - `backend-feature-design-review`
  - `reviewer`
- 输入：
  - 当前 diff
  - 根因和修复方案
  - 回归测试
- 输出：
  - 后端设计审查结果
  - 通用代码审查结果
  - 历史问题 / 本次新增问题 / 本次扩大问题分类
  - 必须修复项
- 是否允许改代码：审查阶段默认否；发现本次新增阻塞问题后，回到执行阶段修复。
- 是否需要用户确认：涉及范围扩大或取舍时需要确认。
- 执行要求：
  - 修复不能引入新的分层、命名、校验、事务或重复逻辑问题。

---

### 9. 回归测试与验证

- 使用：
  - 项目测试命令
  - `superpowers:verification-before-completion`
- 输入：
  - 修复后的代码
  - 回归测试计划
  - 审查修复结果
- 输出：
  - 实际运行命令
  - 回归测试结果
  - 未覆盖点
  - 无法运行时的原因和替代验证
- 是否允许改代码：发现问题时回到执行阶段修复。
- 是否需要用户确认：测试无法运行、需要替代验证或风险较高时需要确认。
- 执行要求：
  - 必须证明原 bug 已被覆盖或解释无法覆盖的原因。

---

### 10. 验收

- 使用：
  - 主 agent
  - acceptance checklist
- 输入：
  - 最终 diff
  - 回归测试结果
  - 审查结果
- 输出：
  - 修复摘要
  - 修改文件
  - 验证命令和结果
  - 剩余风险
  - 建议验收路径
  - 实际使用的 skills / subagents / 替代执行说明
- 是否允许改代码：否。
- 是否需要用户确认：由用户最终验收。
- 执行要求：
  - 最终说明必须包含 bug 复现、根因、修复和验证证据。
