# Backend Feature Workflow

后端功能只在不需要新增或修改前端页面、前端调用链、前后端联调行为时使用。只要用户同时提到页面、接口联调、前端展示、前端调用新接口，必须改判为 `fullstack-feature`。

## 阶段

### 1. `superpowers:brainstorming`

- 使用：
  - `superpowers:brainstorming`
- 输入：
  - 用户原始需求
  - 已知业务背景
  - 项目级 `AGENTS.md` 规则摘要
- 输出：
  - 需求目标
  - 影响范围
  - 不做范围
  - 成功标准
  - 待确认问题
  - 行为变更点
- 是否允许改代码：否。
- 是否需要用户确认：是，需求边界不清时必须先确认。
- 执行要求：
  - 不得用普通“需求分析”替代 `superpowers:brainstorming`。
  - 业务行为、权限、状态流转和历史兼容必须在本阶段说清楚。

---

### 2. 数据库 / 接口设计

- 使用：
  - `api-designer`
  - `sql-pro`
  - 数据库 checklist
  - API checklist
- 输入：
  - brainstorming 结论
  - 现有接口和字段
  - 现有表结构、查询、索引和字典来源
  - 入口层、Service、Mapper/DAO/Repository/SQL 现状
- 输出：
  - API 契约草案
  - 数据库影响说明
  - 数据来源和字段语义说明
  - 权限校验位置
  - 新增或修改查询的调用链
- 是否允许改代码：否。
- 是否需要用户确认：涉及接口兼容、数据库结构、字段语义或权限变化时需要确认。
- 执行要求：
  - `api-designer` 负责接口路径、入参、出参、错误码、兼容性、权限和调用方影响。
  - `sql-pro` 负责表、字段、索引、SQL、迁移、回填、性能和历史数据兼容。
  - 如果 subagent 不可用，主 agent 必须说明原因，并按同等职责给出设计结果。

---

### 3. 后端设计门禁

- 使用：
  - `backend-feature-design-review`
- 输入：
  - 需求和影响范围
  - API 契约草案
  - 数据库影响说明
  - 计划新增或修改的 Controller / Service / Mapper / DAO / Repository
- 输出：
  - 阻塞问题列表
  - 分层设计结论
  - 命名一致性结论
  - 校验位置和事务边界结论
  - save/update 复用设计建议
- 是否允许改代码：否。
- 是否需要用户确认：有阻塞问题或设计取舍时需要确认。
- 执行要求：
  - 本阶段是编码前门禁，不是编码后的 review。
  - `backend-feature-design-review` 指出的阻塞问题必须修正设计后才能进入 `writing-plans`。

---

### 4. `superpowers:writing-plans`

- 使用：
  - `superpowers:writing-plans`
- 输入：
  - 已确认的需求边界
  - 数据库 / 接口设计
  - 后端设计门禁结论
  - 项目构建和测试约束
- 输出：
  - 分步骤实现计划
  - 文件级修改清单
  - 测试计划
  - 风险和回滚方案
  - 子代理分工计划
- 是否允许改代码：否。
- 是否需要用户确认：是，计划未确认前不得进入实现。
- 执行要求：
  - 计划必须体现 `superpowers:executing-plans with TDD`。
  - 计划必须写清楚入口层、Service 方法、数据访问层方法、权限校验位置和数据来源。

---

### 5. 用户确认

- 使用：
  - 主 agent
- 输入：
  - `writing-plans` 输出
  - 阻塞问题处理结论
- 输出：
  - 用户确认结果
  - 需要调整的设计或计划
- 是否允许改代码：否。
- 是否需要用户确认：是。
- 执行要求：
  - 用户未确认前，不得启动实现型 subagent，不得执行迁移，不得修改代码。
  - 用户要求调整时，先修改设计或计划，再重新等待确认。

---

### 6. `superpowers:executing-plans` with TDD

- 使用：
  - `superpowers:executing-plans`
  - `spring-boot-engineer`
- 输入：
  - 已确认的计划
  - 已确认的可修改范围
  - 测试计划
- 输出：
  - 后端实现
  - 新增或调整的测试
  - 实际修改文件
  - 偏离计划的说明
- 是否允许改代码：是，仅限用户确认后的计划范围。
- 是否需要用户确认：进入本阶段前需要确认；阶段内偏离计划时需要再次确认。
- 执行要求：
  - TDD 嵌入本阶段：能先写失败测试或回归测试时，先写测试，再实现。
  - 后端业务实现优先交给 `spring-boot-engineer`；不可用时由主 agent 说明原因并替代。
  - 不允许多个 subagent 同时修改同一文件或同一模块。

---

### 7. 子代理交接与集成回收

- 使用：
  - 主 agent
  - 已启动的 subagents
  - `references/review-and-handoff.md`
- 输入：
  - subagent 交付结果
  - 实际修改文件
  - 测试和验证输出
- 输出：
  - 子代理交接摘要
  - 冲突或缺口处理结果
  - 主 agent 集成结论
- 是否允许改代码：必要时允许，但只能处理集成缺口和冲突，不能扩大范围。
- 是否需要用户确认：交接结果改变计划或风险上升时需要确认。
- 执行要求：
  - 每个 subagent 必须有职责边界、读写范围、禁止事项和交付物。
  - 未启动的计划内 subagent 必须说明原因，并给出主 agent 替代产出。

---

### 8. 代码审查

- 使用：
  - `backend-feature-design-review`
  - `reviewer`
- 输入：
  - 当前 diff
  - 设计门禁结论
  - 项目规则
  - 测试计划
- 输出：
  - 后端架构审查结果
  - 通用代码审查结果
  - 历史问题 / 本次新增问题 / 本次扩大问题分类
  - 必须修复项
- 是否允许改代码：审查阶段默认否；发现本次新增阻塞问题后，回到执行阶段修复。
- 是否需要用户确认：涉及范围扩大或取舍时需要确认。
- 执行要求：
  - `backend-feature-design-review` 在本阶段用于编码后审查，必须再次检查字段语义、命名一致性、分层、校验位置、事务边界、重复逻辑和测试覆盖。
  - `reviewer` 做通用代码审查。

---

### 9. 测试与验证

- 使用：
  - 项目测试命令
  - `superpowers:verification-before-completion`
- 输入：
  - 修改后的代码
  - 测试计划
  - 审查修复结果
- 输出：
  - 实际运行命令
  - 测试结果
  - 未覆盖点
  - 无法运行时的原因和替代验证
- 是否允许改代码：发现问题时回到执行阶段修复。
- 是否需要用户确认：测试无法运行、需要替代验证或风险较高时需要确认。
- 执行要求：
  - 不得伪造测试结果。
  - 后端改动至少运行匹配的单元测试、集成测试、构建检查或静态检查之一。

---

### 10. 验收

- 使用：
  - 主 agent
  - acceptance checklist
- 输入：
  - 最终 diff
  - 测试与验证结果
  - 审查结果
- 输出：
  - 变更摘要
  - 修改文件
  - 验证命令和结果
  - 剩余风险
  - 建议验收路径
  - 实际使用的 skills / subagents / 替代执行说明
- 是否允许改代码：否。
- 是否需要用户确认：由用户最终验收。
- 执行要求：
  - 不得声称完成，除非已有验证证据。
  - 最终说明必须区分已完成、未覆盖和需要用户验收的内容。
