# 视觉证据、判定与复测

## 执行记录

保留页面与版本、状态、触发步骤、参照来源、窗口尺寸与缩放、预期视觉、实际表现、结果、证据和时间。复用已有测试用例与问题编号，在本次运行目录保存执行报告，不自动生成整套协作文档。

截图、视频、控制台和请求证据均需脱敏，不写入凭据、认证头、cookies 或完整敏感响应。

## 报告文件与交付

每次实际视觉测试结束或因故停止，默认必须保存一份 UTF-8 中文 `REPORT.md`。通过、失败、未发现缺陷、环境阻塞和部分执行均适用；不能只在聊天中说“已测”或“通过”。

- 目录优先遵从用户指定位置，其次使用项目已有测试输出目录；本机 Playwright 输出遵守 `playwright-local-runtime`。在输出目录下按日期时间与页面短名创建本次运行子目录，必要时加序号，不覆盖既有运行。
- 截图和必要的过程记录保存在本次运行目录内；报告以相对链接关联。已有证据可引用原位置，不重复生成，但必须注明来自哪次运行、为何仍覆盖当前版本；不得将旧证据伪装成新执行。
- 已执行且判定通过的视觉检查也须有可核验依据；静态检查关联截图，动态检查关联视频、连续截图或位置采样文件，不能只把关键采样数据留在工具输出中。
- 缺陷清单直接放在 `REPORT.md`，除非已有问题系统需要链接，不为相同问题另建重复台账。未发现缺陷时写“已覆盖范围内未发现确定缺陷”，仍列覆盖与证据；受阻时记录停止位置、原因、已执行与 not-run 项，不伪造截图或通过结果。
- 报告不是自动化测试脚本。每次都保存报告，不意味着每次都新建可运行脚本、像素基线或安装测试依赖。
- 保存后核对报告存在、可读取，证据链接可访问且对应本次状态，结论与实际结果一致，并检查脱敏。文件存在和链接校验不替代真实视觉测试。
- 最终回复包含两类视觉结论、缺陷数量、主要限制，以及带绝对路径的可点击报告链接；存在缺陷时优先指出问题及对应证据。

仅预览或策划且未执行测试时，不生成冒充已执行的报告。用户明确要求不落盘、当前模式禁止写文件或无法写入任何获准目录时，遵守限制，在对话给出相同结构的记录及未保存原因；明确报告交付未完成，不声称文件已生成，不擅自改写入其他位置。重新恢复测试时继续记录原运行，复测新版本则新建运行并引用原报告。

### REPORT.md 内容结构

1. 范围与环境：页面、运行时间、版本（未知则注明）、窗口和缩放、参照来源、执行者及使用工具。
2. 两类视觉结论：静态视觉、交互过程的适用性、passed / failed / not-run、总体结论与覆盖限制。
3. 检查清单：每项的页面状态、触发步骤、预期依据、实际表现、状态和证据链接；区分未执行和不适用。
4. 缺陷清单：编号、来源、影响和严重程度、复现步骤、实际与期望、证据、建议负责人及处理状态；无缺陷也明确写明。
5. 修复与复测：关联原缺陷、修复版本、复测步骤和结果；未修复或未复测时注明，不虚构完成。
6. 未覆盖与阻塞：遗漏状态、环境或参照限制、延期项及剩余风险。
7. 职责声明：业务功能正确性未由本 skill 验证；列出实际生成的报告、证据及按需脚本，未生成脚本时如实说明。

## 两类视觉结论

- 静态视觉与交互过程的视觉稳定性分别报告范围、适用性、passed / failed / not-run 和证据。
- 任一适用项 failed，视觉检查未通过；无失败但有适用项 not-run，视觉检查未完成。不适用项说明依据，不冒充 passed。
- 全部适用项有证据通过，只能声明本次已覆盖范围的视觉检查通过；功能正确性注明“本 skill 未验证”。
- 构建、接口或操作成功不能证明视觉合格；最终稳定截图不能证明交互过程合格。
- 如果同时存在独立功能测试，分别引用其需求和执行证据，保留两份结论；不能用视觉通过覆盖功能失败，也不能用功能通过覆盖视觉失败。

## 缺陷记录

每项包括页面或组件、来源分类、严重程度与影响、状态和窗口、步骤、实际与预期、参照、脱敏证据、建议负责人及复测状态。

- 区分历史问题、本次新增和扩大问题；本次新增或扩大的真实缺陷必须修复。延期项单列，不改写原始结果。
- 重叠遮挡关键内容按实际影响报告；已确认的对齐或间距偏差也记录，不因 Minor 标签豁免本次缺陷。
- 合法浮层、内部滚动和明确的文本省略按项目预期判断；无依据的审美意见列为建议，不擅自改设计。

## 修复与复测

1. 仅测试时报告缺陷。修复另获授权后，局部 UI 交给 ui-fixer，较完整前端逻辑交给 frontend-developer；若涉及业务规则或后端，交回相应开发流程，不在视觉测试中直接修复。
2. 诊断、修复与复测分别记录；不改预期、不更新基线来掩盖缺陷。
3. 可自动化时保留修复前失败与修复后通过证据；旧版本不可得时如实说明。
4. 复测原操作、数据表现和窗口，再检查长文本、错误态、相邻尺寸及共享组件受影响路径。
5. 新代码补审并验证最终版本，不能沿用旧提交的证据；清理仍遵守授权。

## 最终输出

范围与版本 → 两类视觉结论 → 缺陷及参照 → 实际执行者与证据 → 复测 → 未覆盖、阻塞和风险。明确“业务功能正确性未由本 skill 验证”。

示例：静态视觉 failed（弹窗按钮遮挡字段），交互过程 not-run，则视觉检查未通过。即使保存操作成功，也不输出业务功能 passed 或完整菜单验收通过。
