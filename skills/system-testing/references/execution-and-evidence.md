# 证据、判定与复测

## 执行记录

每个重要测试保留：用例或临时编号、环境和版本、前置数据、角色、窗口尺寸及缩放（页面适用）、步骤、预期依据、实际结果、执行状态、证据与时间。

复用已有 `TEST-CASES.md`、`ISSUES.md` 或项目测试平台。没有相关文档时，先用对话报告和获准的证据目录；不自动生成团队文档包，不重复建立相同缺陷的台账。

截图、视频、控制台和接口证据均需脱敏。凭据不写入脚本或报告；认证头、cookies、完整敏感响应和带密码的网络记录不得直接输出或打包。

## 三维判定

- 功能正确性、静态视觉、交互过程分别说明适用性、执行状态和证据。
- 适用项使用 `passed`、`failed`、`not-run`；不适用项记录依据，不生成虚假通过。
- 任一适用项 `failed`，整体未通过；仅无失败但有适用项 `not-run`，整体未完成验证。
- 所有适用项有证据通过，才可声明本次已覆盖范围通过；未覆盖范围仍列明。
- 构建、接口或模拟测试通过，不推导页面视觉或真实系统通过；截图正常不推导交互过程通过。

## 缺陷记录

每项包含：编号、页面或接口、来源分类、严重程度与依据、复现条件、操作步骤、实际与期望、参照来源、脱敏证据、建议负责人、修复和复测状态。

来源分为：历史问题、本次新增、本次扩大。新引入或扩大的真实缺陷必须修复；历史问题单列，需有证据和影响说明。用户明确延期的范围单列，不把延期转写成测试通过。

- 关键内容或操作被遮挡、无法继续流程，按实际用户影响报告阻断问题。
- 可确认的局部对齐、间距或密度偏差也记录缺陷；严重程度按影响确定，不用“Minor”豁免本次缺陷。
- 无规范或参照支持的“更好看”判断列为设计建议；需要新的设计取舍时交给用户或 `ui-designer`，不据此擅自重做界面。

## 修复与复测

1. 仅测试任务报告缺陷；已获修复授权时交给所属实现者，局部 UI 交给 `ui-fixer`，较完整前端逻辑交给 `frontend-developer`，后端交给 `spring-boot-engineer`。
2. 诊断与修复分别记录；不在只读阶段改代码，不修改测试预期来适配错误行为。
3. 对可自动化的回归，保留修复前失败及修复后通过证据；无法取得旧版本时如实说明，不补造失败记录。
4. 重现原操作、相同数据状态和窗口条件，再检查长文本、错误态、相邻尺寸及共享组件受影响路径。
5. 新代码按实际范围补审和验证；使用最终版本的证据，不用修复前或旧提交的报告验收。
6. 测试数据、证据或临时文件的清理遵守删除确认要求；未获授权时保留并报告路径。

## 最终输出

报告顺序：范围与版本 → 三维结论 → 缺陷及来源 → 实际执行与证据 → 修复复测 → 未覆盖、阻塞和风险。实际角色和主代理替代职责如实记录。

示例：功能 `passed`，静态视觉 `failed`（弹窗按钮遮挡字段），交互过程 `not-run`（该过程尚未验证），整体结论为未通过；不能因保存成功或已提供截图改为通过。
