# 系统与页面测试

分别验证功能正确性、静态视觉和交互过程，输出可复现的证据、缺陷与覆盖缺口。既可独立调用，也可作为 `development-workflow-router` 已有测试阶段的执行规范。

## 入口与范围

- 用户只要求测试时，确认已有输入即可执行，不强制进入业务开发流程或重新生成实现计划。测试范围不清时只补问会影响执行的信息。
- 消费 router 已确认的测试计划、权限、数据和执行方式，不重排其阶段；`prompt-preview` 只描述测试，`review-only` 不写测试或业务代码，其他模式也不自动授权子代理。
- 测试策划、自动化脚本实现、真实环境执行分别说明范围。编写测试脚本不等于已验证真实系统。
- 先读取 [测试范围与功能](references/scope-and-functional.md)；有页面时读取 [视觉与交互检查](references/visual-and-interaction.md)；结果和缺陷按 [证据、判定与复测](references/execution-and-evidence.md) 记录。

## 执行约定

1. 明确范围、环境、版本、账号角色、数据及视觉参照。增量改动覆盖受影响路径，系统验收按用户指定的菜单或模块范围执行。
2. 按风险选择页面 × 操作 × 状态 × 窗口尺寸，不机械遍历全部组合。保留正常、异常、边界、权限和受影响的跨模块路径。
3. 先复用项目已有测试、组件、同类页面和脚本；不擅自新增框架、依赖、环境配置或全局设计标准。
4. 执行功能检查；页面任务另外执行静态视觉和真实交互过程检查。接口、数据库和构建结果不能代替浏览器验收。
5. 对发现记录步骤、预期依据、实际表现及脱敏证据。已知历史问题与本次新增、扩大问题分开，主观偏好列为设计建议。
6. 测试并修复已获授权时，将缺陷交给所属实现者，在已确认范围内修复；仅测试时报告缺陷，不直接修改业务代码。
7. 修复后复测原问题及相邻状态、窗口尺寸和共享组件路径；有新代码时补审改动并重跑受影响测试。交付针对最终版本。

## 角色选择

先检查用户授权、当前工具实际支持的角色和模式限制；未获授权或角色不可用时，由主代理承担相应职责并说明，不能虚构独立测试。

| 角色 | 触发与交付 | 边界 |
| --- | --- | --- |
| `qa-expert` | 风险、跨模块或多状态测试需要策划时，输出范围、数据、覆盖缺口和验收条件 | 只读分析，不修改代码，不默认要求穷举 |
| `test-automator` | 需要持久回归脚本、fixture 或既有测试改进时，输出测试改动和执行证据 | 仅已授权的测试及必要测试配置范围；不修业务代码，不擅自装依赖 |
| `ui-ux-tester` | 真实页面的用户流程、视觉与交互验收，输出覆盖和缺陷证据 | 浏览器操作及证据记录，不改业务代码 |
| `browser-debugger` | 遮挡、溢出、抖动或其他浏览器失败的原因不清时，输出复现和定位证据 | 复用已收集证据，不在诊断中修改业务代码 |
| `ui-fixer` / `frontend-developer` | 修复已获授权时，按局部 UI 或前端逻辑边界选择 | 退回已确认实现范围，不同时修改同一文件 |
| `spring-boot-engineer` | 缺陷涉及后端且修复已获授权时处理 | 遵守后端设计门禁与分层，不借测试扩大业务修改 |
| `reviewer` | 测试脚本和修复产生代码改动后，审查行为断言与回归风险 | 只读代码审查，复用覆盖当前 diff 的证据 |

## 配合的 skills

- `ui-ux-pro-max`：进行 UI 规范、体验、可访问性或视觉一致性判断时使用；项目已有规范和同类组件优先。对已证实的遮挡、溢出可直接报告证据，不为调用技能重新设计页面；规则不明确的视觉取舍由 `ui-designer` 协助，必要时由用户确认。
- `playwright-local-runtime`：本机 Windows Playwright / MCP / wrapper 执行时，读取已安装版本的浏览器、运行时及可写目录约定。其他环境遵循项目自身配置，不复制个人路径。
- `superpowers:systematic-debugging`：失败原因不清时使用，不凭截图猜测根因。
- `superpowers:test-driven-development`：新增回归测试或进入已授权修复时使用，确认旧行为失败、修复后通过。
- `superpowers:verification-before-completion`：核对最终结果，复用仍覆盖当前版本的证据，不把未执行说成通过。
- `feature-doc-pack`：仅在用户需要协作文档时复用其测试和问题记录；不因测试自动生成整套文档。

## 必须独立报告的结论

| 维度 | 是否适用及依据 | 执行状态 | 覆盖与证据 / 未执行原因 |
| --- | --- | --- | --- |
| 功能正确性 | 根据本次测试范围填写 | `passed` / `failed` / `not-run` | 操作、接口、必要的数据状态与证据 |
| 静态视觉 | 页面测试适用；纯后端可说明不适用 | 适用时填写三种状态之一 | 参照组件、页面状态、窗口及截图 |
| 交互过程 | 存在相应页面交互时适用 | 适用时填写三种状态之一 | 加载、弹窗、展开、滚动及过程证据 |

任一适用维度 `failed`，整体未通过；无失败但有适用项 `not-run`，整体未完成验证；全部适用项有证据通过后，才报告“本次已覆盖范围通过”。不适用项说明依据，不冒充 `passed`。用户明确延期的问题单列，不改写原始测试结果。

交付包含测试版本、范围与遗漏、三维结论、缺陷来源、实际执行角色、证据路径、复测结果和剩余风险。没有实际浏览器操作时，不宣布页面验收通过。
