# Change Management

用于完整文档包、提测发布、变更记录和问题跟踪。

变更发布层只记录本次变化、风险和交付检查，不替代 `PLAN.md`、`BUSINESS-RULES.md`、`API-CONTRACT.md`、`DATABASE-DESIGN.md`、`TASK-BOARD.md` 或 `TEST-CASES.md`。

## 触发条件

当需求满足以下任一情况时，生成或更新变更发布层文档：

- 用户选择完整文档包。
- 涉及提测、上线、灰度、回滚或发布检查。
- 涉及接口、字段、业务规则、数据库设计或兼容策略的可见变化。
- 存在跨团队阻塞、联调问题或遗留风险。
- 用户要求记录变更、问题或发布计划。

## Delta-first 原则

`CHANGELOG.md`、`ISSUES.md` 和 `RELEASE.md` 应优先记录“本次相对既有事实发生了什么变化”。

- 不复写完整需求说明。
- 不把所有业务规则复制到变更记录里。
- 每条变化尽量链接到对应的 `BR-xxx`、`API-xxx`、`DB-xxx`、`TASK-xxx` 或 `TC-xxx`。
- 未确认内容写入待确认或风险，不写成已定结论。

## CHANGELOG.md 推荐结构

1. 变更状态
2. 变更日期
3. 新增内容
4. 调整内容
5. 移除内容
6. 兼容影响
7. 关联规则、接口、数据库设计、任务和测试
8. 待确认项

每条变更应说明影响对象、变更原因、影响范围和追踪编号。

## ISSUES.md 推荐结构

1. 问题编号
2. 问题描述
3. 影响范围
4. 严重程度
5. 状态
6. 负责人或待分配角色
7. 下一步动作
8. 关联规则、接口、数据库设计、任务和测试

问题状态建议使用：`待确认 / 待处理 / 处理中 / 已解决 / 暂缓 / 关闭`。

## RELEASE.md 推荐结构

1. 发布目标
2. 发布范围
3. 不在本次发布范围
4. 前置条件
5. 数据迁移或兼容检查
6. 发布步骤
7. 回滚策略
8. 验证清单
9. 风险和监控
10. 发布结论

如果存在数据库变更，`RELEASE.md` 应引用 `DATABASE-DESIGN.md` 或后端技术设计阶段确认的迁移文档。feature-doc-pack 阶段不默认输出最终可执行 DDL。

## 质量门槛

- 变更记录必须能追踪到协作事实层，不产生孤立条目。
- 问题必须有状态、影响范围和下一步动作。
- 发布检查必须区分发布前、发布中、发布后验证。
- 涉及数据库变更但 `DATABASE-DESIGN.md` 未确认时，发布状态不能写成可发布。
- 不要把变更发布层写成系统总说明或长期路线图。
