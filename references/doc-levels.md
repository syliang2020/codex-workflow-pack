# Document Levels

用来判断用户选择 2、3、4 时应生成或更新哪些文件。

## 前置模式：REQUIREMENTS.md

`REQUIREMENTS.md` 是输入层文档，不属于最小、标准或完整文档包的默认文件清单。

适用于：

- 只有口述需求、截图、聊天记录或零散反馈。
- 目标、范围、用户角色、业务规则、接口、数据边界不清。
- 用户希望先把需求事实和待确认问题整理清楚，再决定是否生成协作文档包。

生成或更新：

- `REQUIREMENTS.md`

生成后停止，等待用户确认。不要自动继续生成 `PLAN.md`、`BUSINESS-RULES.md`、`API-CONTRACT.md`、`TASK-BOARD.md` 或 `TEST-CASES.md`。

## 最小文档

适用于：

- 单模块小迭代
- 小范围接口调整
- 1 到 2 人可完成的需求

生成或更新：

- `PLAN.md`
- `API-CONTRACT.md`，仅在涉及接口时
- `BUSINESS-RULES.md`，仅在业务规则复杂、需要共享细则时
- `DATABASE-DESIGN.md`，仅在涉及数据库变更时

最小文档通常不强制单独写进度视图，但如果涉及多人协作，应在 `PLAN.md` 或 `TASK-BOARD.md` 中至少标明负责人和状态。

## 标准文档包

适用于：

- 2 人及以上协作
- 前后端联调
- 跨模块改动
- 中等复杂度需求

生成或更新：

- `PLAN.md`
- `BUSINESS-RULES.md`
- `API-CONTRACT.md`
- `TASK-BOARD.md`
- `TEST-CASES.md`
- `DATABASE-DESIGN.md`，仅在涉及数据库变更时

其中 `TASK-BOARD.md` 必须包含进度视图，至少能看出负责人或待分配、状态、依赖、阻塞和完成标准。

## 完整文档包

适用于：

- 跨仓库协作
- 多团队参与
- 风险较高
- 需要持续联调和问题追踪
- 提测或发布链路复杂

生成或更新：

- `PLAN.md`
- `BUSINESS-RULES.md`
- `API-CONTRACT.md`
- `TASK-BOARD.md`
- `TEST-CASES.md`
- `CHANGELOG.md`
- `ISSUES.md`
- `RELEASE.md`
- `DATABASE-DESIGN.md`，仅在涉及数据库变更时
- `PROGRESS.md`，仅在多人长期协作、用户要求单独看进度、或任务板过大时生成

## 文件职责

- `REQUIREMENTS.md`：输入层需求草案，收敛需求背景、目标用户、业务目标、范围、不做内容、验收标准和待确认问题；它不是默认文档包成员。
- `PLAN.md`：说明本次改动做什么、不做什么、谁负责什么、里程碑、风险点、验收标准。只放业务规则摘要。
- `BUSINESS-RULES.md`：说明详细业务规则，包括状态流转、字段级规则、复杂校验、模式差异、限制条件、统计口径、异常提示、边界场景；不写 DDL、索引、迁移、回填或回滚 SQL。
- `API-CONTRACT.md`：说明接口、字段、错误码、枚举值、请求响应结构和必要数据映射；不写数据库迁移脚本。
- `DATABASE-DESIGN.md`：说明本次改动涉及的数据模型和数据库设计草案，包括表清单、表关系、字段草案、主键、唯一约束、索引建议、字典映射、数据迁移影响和历史数据兼容方案；不默认输出最终可执行 DDL。
- `TASK-BOARD.md`：拆分角色或负责人任务，避免多人重复开发或边界冲突，并记录任务状态、依赖和阻塞。
- `TEST-CASES.md`：记录联调点、验收点、边界和异常场景，并映射业务规则和接口编号。
- `CHANGELOG.md`：记录接口、字段、规则变化，仅在确实发生变化时更新。
- `ISSUES.md`：记录联调或开发中的问题。
- `RELEASE.md`：用于提测、上线、回滚和发布检查，仅在需要交付发布时使用。
- `PROGRESS.md`：独立记录总体进度、里程碑、阻塞、风险和下一步动作，仅在进度信息会让任务板过重时使用。

## 条件文档

条件文档不属于每次都必生成的默认文件；只有命中对应条件时才生成或更新。

- `DATABASE-DESIGN.md`：当需求涉及新增表、修改表、字段变更、索引、数据关系、数据迁移、历史数据兼容或持久化统计口径时生成或更新。
- `REQUIREMENTS.md`：仅在需求边界不清且用户选择前置模式时生成或更新。
- `CHANGELOG.md`、`ISSUES.md`、`RELEASE.md`：属于变更发布层，通常随完整文档包生成；标准或最小文档包只有在用户明确需要变更记录、问题跟踪、提测或发布检查时才生成。

## 变更发布层

变更发布层用于管理“这次相对既有事实变了什么”，不能替代协作事实层。

- `CHANGELOG.md` 记录范围内新增、调整、移除和兼容影响，优先按编号链接到规则、接口、数据库设计、任务和测试。
- `ISSUES.md` 记录阻塞问题、未决问题、影响范围、负责人或待分配角色、状态和下一步动作。
- `RELEASE.md` 记录提测、发布、回滚、迁移、监控和验收检查。
- 这些文件应遵循 delta-first 原则：先写本次变化，不复写整套系统说明。

## 追踪编号

开发前、开发中、标准文档包和完整文档包应优先使用稳定编号：

- 业务规则：`BR-001`
- 接口：`API-001`
- 数据库设计：`DB-001`，仅在存在 `DATABASE-DESIGN.md` 或项目已确认的迁移文档时使用
- 任务：`TASK-FE-001`、`TASK-BE-001`、`TASK-QA-001`
- 测试用例：`TC-001`

编号用于串联“业务规则 -> 接口 -> 任务 -> 测试”。不要求为每一句话编号，但关键规则和关键接口必须可追踪。
当维护数据库设计文档时，`DB-xxx` 也应被任务和测试用例引用，并能跳转到 `DATABASE-DESIGN.md` 或项目迁移文档中的对应条目。
